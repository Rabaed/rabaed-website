## Comments

**How much of it is already done.** `npm run cms:freeze-seed` does the work: add a migration to `IMPORTS` in `scripts/freeze-seed.ts`, run it, and it writes the statements out beside the words. `npm run cms:migrate-fresh` says in about thirty seconds whether the chain still runs on a database built from scratch. `docs/deployment.md` describes both under "What a data migration may and may not do".

**Where it will need thought, rather than the tool.**

- **The five that hold their words inline.** `publish_contact_points` and the four form wordings have their Arabic written out in the migration itself, not in a frozen module beside it. Freezing them moves the words into generated SQL, where nobody can read them. Each wants its words lifted into a `words.ts` of its own first, as the nine have, so that the readable record survives — and so that the test holding the frozen SQL to the frozen words covers them too.
- **The legal documents are dated on purpose — and need nothing new.** `import_legal_documents` sets every timestamp to 1 September 2026, the day the approved text carries. This ticket first read that as a gap in the freezer, which writes a timestamp column as `now()`. It is not: the dates are set by two plain `UPDATE` statements at the end of the `up`, and SQL beside the seed is exactly what survives a freeze. Keep those two statements after the frozen seed and the three documents come out dated as they are today. The same goes for the launch articles' `publishedAt`, which is an ordinary column, not one of the four the freezer holds at `now()`, so it freezes as written.
- **The launch articles upload their covers.** Like the Trust strip's marks, those stay `payload.create`, and the rows that point at them are found by file name. `import_launch_articles` also creates the posts as drafts, and its `down` reads them back through Payload to delete the covers with their files — that part is a rollback and stays.

**One of the eight arrived while ticket 63 was being built.** `publish_tool_download_wording` was written on ticket 30's branch at the same time, and merged in afterwards, so it was never going to know about a rule that did not exist yet. That is the argument for the list living in a test rather than in a note: a branch that adds a ninth fails the suite on the day it merges.

**Why it is worth doing rather than waiting for it to bite.** Ticket 43 writes the English blog and the English case studies, and ticket 42 the English pages: a field added to Posts, to the FAQs or to the legal documents is the likely shape of all three. Each would stop every fresh database at a migration nobody touched, with an error pointing at a column that migration never mentions — which is exactly the half-day ticket 63 spent working out the first time.

## Agent Brief

**Category:** bug — latent, and the same one ticket 63 closed for the other nine.

**Summary:** Bring the last eight data migrations over to frozen SQL, so that a
field added later cannot stop a database built from scratch at a migration
nobody touched.

**Current behavior:** Eight data migrations write their rows through Payload's
local API. Such a call builds its statement from the fields the code declares
*today*, so the first field added to what one of them seeds makes it name a
column the database has not reached yet, and a fresh database — the test
server's, a preview's, a new deployment's — stops there with `column … does not
exist`. Production, having migrated before the column existed, never notices.
`NOT_YET_FROZEN` in the data-migrations unit test names all eight exactly.

**Desired behavior:** Each of the eight writes its rows as SQL frozen the day it
was written, in the same shape as the nine ticket 63 brought over: a readable
words module beside the migration, a generated `seed.ts` next to it, and an `up`
that executes the seed. `NOT_YET_FROZEN` is empty, and the only Payload call
left in any `up` is an upload.

**Key interfaces:**

- `IMPORTS` in the freeze-seed script: each of the eight gains an entry naming
  its migration, the directory its frozen words live in, and the export to
  write the SQL under. `import_launch_articles` needs the `excludes` option set
  for `media`, the way the Trust strip's import already does, so that the rows
  pointing at a cover look it up by file name rather than by the id of the
  moment.
- `NOT_YET_FROZEN` in the data-migrations unit test: shrinks by one as each is
  converted, and ends empty. The list is exact on purpose — converting one
  without striking it off fails, and so does adding a ninth.
- `FROZEN` in the same test: gains an entry per newly frozen import, so that the
  rule holding frozen SQL to frozen words covers it. This is the reason the five
  inline ones need their words lifted out first.
- A `words.ts` (or equivalently named module) beside each of the five that hold
  their Arabic inline: the site settings' contact points and the four form
  wordings. Same shape as the nine existing `src/migrations/*-import/` modules.

**Order to work in:** lift the five sets of words out first; then add all eight
to `IMPORTS` and freeze in one pass. The freezer replays the whole chain against
an empty database on each run, so one pass over eight is much cheaper than eight
passes.

**Acceptance criteria:**

**Out of scope:**

  applied them by name; Payload matches applied migrations by name, so a rename
  makes those databases try to build the same types and tables a second time and

**Resolved, 22 September 2026, branch `ticket-68`.**

**The words did not change, shown three ways.** Freezing the eight as they
were, then again with the five sets of inline words lifted into their own
`words.ts`, then again with every `up` on its seed, gave the same eight files
each time. The one exception is the legal documents' seed between the first two
runs, which differed only in the 80 ids Payload gives the clauses' list rows,
new on every run through its API. Those are fixed now that the migration runs
its seed, as the home page's 116 have been since ticket 63. The nine older
seeds were untouched by every run.

**The trap is closed, shown both ways.** With a throwaway field added to the
site settings and its migration generated, `npm run cms:migrate-fresh` ran the
whole chain from nothing. With the contact points migration put back on
Payload and nothing else changed, it stopped at that migration, from 13
September, with `column "version_probe_field" does not exist`. The experiment
was thrown away.

**The test has teeth.** `NOT_YET_FROZEN` is empty. `FROZEN` holds all eight to
their words, and changing one word of the demo request form's heading turns it
red. It now reads a value stored as rich text in its JSON-escaped form too:
three paragraphs of the Terms contain a double quote, which JSON writes
escaped.

**What else went.** `toRichText` and `toLegalDocumentFields` had no caller left
once their migrations ran seeds, so they were removed. The shapes the words are
written in stay. The legal documents' recorded author, «استيراد النص المعتمد
قبل الإطلاق», is `IMPORTED_BY` in `legal-import/approved-text.ts`, where the test
can see it.

**The full suite:** 1105 of 1106 on `TEST_PORT=3168`, 20 workers. The one was
`read ECONNRESET` on the legal documents API, early in the run. It is a dropped
connection, not an answer from the server. The legal documents' tests then
passed 23 of 23 in three separate runs, each on a fresh server.
