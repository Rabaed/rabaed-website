# 51: Split the CI tests across four machines

**What to build:** The `test` check runs the end-to-end suite on four GitHub machines at once, each with its own quarter of the tests, so a pull request waits about five minutes for its result instead of about fifteen.

**Blocked by:** nothing.

**Status:** resolved

- [x] The suite runs on four machines in parallel, each with a different quarter of the tests, and together they run every test exactly once
- [x] The pull request still shows one check named `test`, the name `docs/github-ruleset.json` requires, and it fails if any machine fails or is cancelled
- [x] Typecheck runs once, not on every machine
- [x] A failing machine uploads its own Playwright report
- [x] The time a pull request waits for `test` is measured before and after

## Why

A pull request waited 13–15 minutes for `test` on 13 September 2026 (PR #17). Setup and the build took about a minute. The rest was the suite, and the runner's log says why: "Running 585 tests using 1 worker". Playwright uses half the machine's cores by default, and the hosted runner for this private repository is small enough that half its cores is one. The same suite takes about 1.5 minutes on a 20-core development machine with 10 workers.

Two other options were considered and not chosen:

- **Two workers on the same small runner** would save less, and ticket 50 shows what load does to the timing-sensitive tests.
- **Larger paid runners** are a billing decision for the founder.

**What was built.** `.github/workflows/ci.yml` now has three jobs.

- **`e2e (1/4)` to `e2e (4/4)`** start together from one matrix. Each installs, builds the site through Playwright's web server, and runs `npm test -- --grep-invert @pixel --shard=N/4`.
  - `fail-fast: false`, so one run reports every failing test, not only one machine's.
  - A failing machine uploads its report as `playwright-report-<index>`. Each machine gets its own name, because two uploads under one name fail.
- **`typecheck`** runs once, on a machine of its own, in parallel with the tests.
- **`test`** runs after both and passes only if both succeeded. It keeps the single check name `docs/github-ruleset.json` requires. It runs with `always()`, because a required check that is skipped — as it would be after a failed or cancelled machine — counts as passed.

`docs/deployment.md` says the tests are split and shown as one check.

**Checked locally.** `npx playwright test --list --grep-invert @pixel` lists 646 tests. With `--shard=1/4` to `4/4` it lists 162, 162, 161 and 161. Together those are exactly the whole list, and none appears twice. The split is by test rather than by file because `playwright.config.ts` sets `fullyParallel: true`.

### Measured

PR #19's first run (`34775199220`) passed, and every machine ran its shard with one worker.

**Before:** PR #17's `test` took 13m16s and 15m30s.

**After:** the whole run took 6m44s, from 18:37:27 to 18:44:11.

| Job | Tests | Time |
| --- | --- | --- |
| `e2e (1/4)` | 162 | 6m35s |
| `e2e (2/4)` | 162 | 5m16s |
| `e2e (3/4)` | 161 | 3m25s |
| `e2e (4/4)` | 161 | 2m55s |
| `typecheck` | — | 24s |
| `test` | — | 4s |

**The shards are uneven.** Playwright divides by test count, not duration, and shard 1 holds most of the Reference-site comparison specs. The wait is therefore set by the slowest machine. Balancing them could bring the run to about 4–5 minutes; that is a possible follow-up, not this ticket.

### For whoever merges second

PR #18, the Next.js build cache, adds a step to the old single job. If this merges first, that step moves into the `e2e` job, so all four machines restore the cache.
