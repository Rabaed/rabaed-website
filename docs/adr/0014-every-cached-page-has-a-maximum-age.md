# Every cached page has a maximum age, and it is ten minutes

Every page of this site is built ahead of time and rebuilt when a publish marks it stale — `refreshSite` in `src/cms/revalidation.ts`, which marks all twenty pages and the three discovery files, each rebuilt on its next visit. That is the standard Payload and Next pattern and it is the right way for a change to travel: an Editor publishes and the words are on the site in under a second.

What it has no answer for is a mark that goes astray. The mark is the *only* thing that ever rebuilds a page, so anything that loses one leaves that page showing the words from before the publish — not for a while, but **until somebody publishes again**. Ticket 64 found the first way this happens and it is not exotic: a render that began before a publish and finished after it writes the old words into the cache stamped with the moment the write finished, and Next decides freshness by that stamp rather than by what is in the page, so it counts them as fresh and serves them indefinitely. A hook that throws, a request that never lands, a region that missed the mark would each do the same, and we cannot enumerate the ones we have not met.

So there is now a floor under all of them. `src/app/(ar)/layout.tsx` and `src/app/(en)/en/layout.tsx` each set `export const revalidate = 600`, and because a route takes the lowest age in its segment chain, that one line covers all twenty pages beneath each. `src/app/llms.txt/route.ts`, `src/app/robots.ts` and `src/app/sitemap.ts` set their own, being routes beside the layouts rather than beneath them — the same three, and the same reason, as `DISCOVERY_FILES` in `revalidation.ts`.

**Ten minutes, and why ten.** The number answers "how far behind may a page be when something has gone wrong". It is not a publishing delay: publishing is untouched and still arrives in under a second. Ten minutes is comfortably inside the time an Editor would take to notice a page had not changed and publish again, so the floor heals the failure before a person would reach for it; and it costs about half the rebuilds of five minutes, which buys nothing more for a failure this rare. An hour would stop reading as a backstop and start reading as a tolerance for wrong words. This was the founder's decision on 22 September 2026.

**What it deliberately is not.** It does not close ticket 64's window. A page caught by that race is still wrong; this bounds how long it stays wrong, turning "until somebody publishes again" into "ten minutes". Closing the window means marking every page twice per publish and keeping the server awake between the marks, which costs every publish something to fix a rare one — that is ticket 64's decision, and this is the cheaper thing that covers more, taken first on purpose so that the harder decision can be made with real numbers behind it.

## Consequences

- **The bound is the age plus one render, and it is the second visitor who sees the change.** Next rebuilds when somebody asks for a page whose age has run out, not on a timer, and it serves the visitor who triggered it the old page while the rebuild happens behind them. Ten minutes is therefore "how stale may a page be", not "when will it be right for everybody".
- **A window in which nobody visited costs nothing**, which is most windows on most pages of a marketing site. At worst it is one extra render per page per window, and only for the pages somebody actually asked for.
- **The number is written out in five files rather than imported into them.** Next reads `export const revalidate` by static analysis and accepts only a literal — `revalidate = 600` is valid, `revalidate = 60 * 10` is not. `src/lib/cache-age.ts` holds `MAX_PAGE_AGE_SECONDS` with the reasoning, and `tests/unit/cached-page-age.spec.ts` holds every one of the five literals to it, so the five cannot drift apart.
- **The test reads the build, not only the source.** The whole point of setting the age on two layouts rather than twenty pages is that a page inherits its parent's; a test of the source alone would assume that inheritance rather than show it. So the spec also reads `.next/prerender-manifest.json` and asserts that every prerendered visitor route was built with the age — seventeen of them, against the studio and framework routes left at `false`. A new page group added without an age fails there.
- **The Screen mock studio is deliberately excluded**, along with `(payload)` and `(forms)`. The studio is built from HTML on disk (ADR-0002) and changes only when a deploy changes it, so no publish can make it stale and there is nothing for a floor to catch; the admin and the form API routes are not cached at all.
- **This is the previous caching model.** `revalidate` as a route segment config is removed when Cache Components is enabled, which this project does not enable; the installed Next is 16.3.5 and documents it under `01-app/02-guides/caching-without-cache-components.md` rather than in the segment-config reference, which makes it look removed when it is not. The day Cache Components is turned on, this decision moves to `cacheLife` and has to move deliberately.
- **It changes nothing about how a change travels in the ordinary case**, which is the thing worth not breaking: the publish waits across the suite still see a change arrive in well under the budget, and on-demand marking is untouched.
