# The confirmation email is capped, and no challenge is added

Every form sends a confirmation to the address the visitor typed, greeting them by the name they typed (user story 26). That makes each form a way to have Rabaed's own mailbox send a message of somebody else's choosing to an address of somebody else's choosing: a script puts its advert in the name field and a stranger's address in the email field. The spec's spam protection — "a honeypot field plus rate limiting per address, with a challenge added only if abuse appears" (spec: Forms) — stops a careless bot, not that: the trap field is easy to leave empty, the form's one-off token is easy to make up, and five requests an hour from each of a few hundred network addresses is a great deal of mail. Mail providers judge a domain by what it sends, so the cost of abuse falls on every email the team sends afterwards, not only on the forms. The architecture review of 24 September 2026 found it (ticket 81).

The obvious answer is a challenge — Cloudflare Turnstile, say — and the founder chose on 24 September 2026, eight days before launch, **not to add one**, keeping the spec's rule, and to make a confirmation worth nothing to anybody abusing it instead:

- **One address is sent at most three confirmations in 24 hours**, whatever form, language or network address the requests come from, its letters compared without case. Three covers a person who sends two forms and resends one.
- **The site sends at most 30 confirmations an hour.** The launch expects a handful of requests a day; thirty in an hour is abuse or an event big enough that the team should be answering by hand anyway.
- **A request over either limit is still stored and the team still alerted.** Only the visitor's confirmation is not sent, and its record says so in the admin (`withheld`, «لم تُرسل — بلغ هذا البريد أو الموقع حدّ رسائل التأكيد، فالرد يدوي»), so the team knows to reply by hand. Nothing a person sent is lost to the limit. From the moment a confirmation is counted against the limit to the moment its outcome is known, its record says `sending` («قيد الإرسال»), never sent before it is.
- **The name goes into the greeting only when it reads as a name**: at most 60 characters, with no digit in any script, no «@», no link and nothing shaped like a web address. Otherwise the placeholder and the space before it are left out, so «مرحباً {الاسم}،» reads «مرحباً،» and "Hello {name}," reads "Hello,". An engineer's «م.» before a name is kept. The team's alert still shows what was typed.
- **The limits are exact under requests sent at once.** Counting and then storing let requests sent in the same moment each count the same number, and all get through. Both the five-an-hour limit and the confirmation limits now count and write inside a transaction holding a Postgres advisory lock (`pg_advisory_xact_lock`) — one per network address for requests, one for the whole site for confirmations — so a second request waits for the first to be counted and written. The lock is held for a count and one write, never while documents upload, and a wait longer than five seconds fails the request rather than queueing without end.

## Considered options

- **Cloudflare Turnstile now.** It stops abuse before anything is stored, and it would have been the right answer if abuse had appeared. It needs a Cloudflare account and two keys set on Vercel before launch, loads an outside script on every page with a form, and has to be named in the Privacy Policy and the privacy inventory, which the lawyer is already revising. It also overrules a rule the spec states deliberately. It stays the next step, **if abuse appears**, which is when the spec says to take it.
- **Both.** Most protection, with every cost of Turnstile before launch.
- **No confirmation at all.** Takes away something the spec promises every applicant (user story 26), to stop something the caps already make worthless.

## Consequences

- **A person can go unconfirmed.** A fourth request from one address in a day, or any request past the thirtieth in an hour, is answered on the page but gets no email. The record says `withheld`, and the team replies by hand.
- **The site-wide limit is not driven by the test suite.** Filling it would withhold the confirmation every other suite running beside it expects: they share one test server and database. The per-address limit runs through the same count, lock and claim and is tested end to end, including requests sent at once; the thirty is a number in that same query. Were the suites that publish given a server of their own, this could be tested too.
- **Requests from one network address sent at once wait for each other**, for as long as a count and a write take. Each waiting request holds a database connection while it waits, so a burst from one address holds as many connections as it has requests, for milliseconds each.
- **An address is compared as typed, apart from case.** `name+1@gmail.com` counts as a different address from `name@gmail.com`; the site-wide limit is what bounds that.
